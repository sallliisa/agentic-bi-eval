# Cloudflare OS context selection

Checked source: `cloudflare/cloudflare-os` commit `004ab773fad6d4fb7fe67be920a3ef37e46dc58a`, the checkout referenced by this project’s runner notes.

## Finding

Cloudflare OS supports selecting a model and attaching resource capsules when a client creates a chat. Its current chat API does not accept a list of context collection IDs or a per-chat context filter. The Context Library is attached as an ambient resource and gives the agent access to all collections visible to the account. Therefore the test runner cannot enable only chosen collections through the existing `newChat` call.

## Evidence

- `Overseer.newChat` takes an initial message, model ID, optional `CapsuleSpecifier[]`, attachments, and display formats. It has no collection-selection parameter. The authenticated implementation gets chat context for the chosen model, then passes the optional capsules to the chat creation path. ([API declaration](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/workshop-shared/src/api.ts#L2180-L2194), [implementation](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/workshop-backend/src/overseer.ts#L11794-L11800))
- A capsule points to a `gatekeeperId` workpiece and replaces a span in the chat message. It does not point to a context collection. ([`CapsuleSpecifier`](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/workshop-shared/src/api.ts#L3570-L3606))
- The Context Library loads all private collections owned by the account and all public collections in the sharing domain. `listEnabledContextCollections` returns that complete set. ([collection loading](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/context-api.ts#L20-L54), [enabled collection API](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/context-api.ts#L258-L262))
- Each workspace provisions singleton accounts, including the Context Library, as ambient gatekeepers. They are folded into each chat’s environment. The Context Library agent catalog is built from all enabled collections. ([ambient provisioning](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/workshop-backend/src/overseer.ts#L7537-L7557), [catalog generation](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/library-gatekeeper.ts#L321-L331))
- The context read API can search or list one collection by ID, but it checks that the collection is in the account-wide enabled set. This supports filtering an individual read, not restricting the agent’s chat capability to a selected subset. ([collection search](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/library-read.ts#L78-L92), [collection listing](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/library-read.ts#L185-L216))

## Impact for the test runner

Model choice is supported by the existing `newChat` model argument. Whole-collection selection needs a Cloudflare OS change that gives the Context Library a per-chat collection scope, or a separate constrained context capability. Adding the selected collection names to the user prompt would only be guidance: it would not remove the ambient capability to search other enabled collections.

The current OS also has no account-level enable/disable switch for collections. Its enabled set is computed from all private collections owned by the account and all public collections in the sharing domain. The Context & Skills page only lists this set; its collection actions edit or delete collections. A global switch would change the context available to other chats too, so it would not give a run its own collection selection.

- The owned-plus-public set is constructed directly by `loadEnabledContextCollections`, and the user library returns that set for agent reads. ([collection loading](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/context-api.ts#L20-L54), [`getEnabledCollections`](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/src/user-library.ts#L80-L94))
- The Context & Skills page loads the collection list and renders it; no enable/disable operation is exposed there. ([page list](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/app/ContextLibraryPage.tsx#L947-L982), [collection actions](https://github.com/cloudflare/cloudflare-os/blob/004ab773fad6d4fb7fe67be920a3ef37e46dc58a/packages/gatekeeper-context/app/ContextLibraryPage.tsx#L1400-L1420))
